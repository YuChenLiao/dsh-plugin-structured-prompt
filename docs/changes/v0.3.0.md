# v0.3.0 —— 接上公开提示词库（宿主代发检索）（2026-10）

本文件归档这一批改动：把 prompts.chat 的公开提示词检索接进插件，作为"提示词从哪来"的**第二条
路径**。它与表单构建器完全隔离 —— 检索到的是别人写好的成品文本，只被预览与发送。

分支：`feat/prompt-library`（提交时先建分支）。

## 起点：为什么不做上一批挂着的 C 项

v0.2.3 / v0.2.4 的归档里都挂着一项未决（C）：把「本机自定义模板」长期化（插件内新开一个 Cordis
服务 + localStorage 单键 + `inject` 的 `hooks` 隔间给组件）。本批**不做它**，改走"接一个现成的
公开提示词库"。

理由要说清，否则下次会误以为两者等价：C 解决的是"人把自己的**表单片段**跨会话复用"（产物是
`Partial<PromptForm>`，能填进表单继续编辑），而 prompts.chat 提供的是**成品提示词文本**
（title / description / content）。两者不在同一层，prompts.chat 补不上 C 的那个洞。放弃 C 的真实
代价是「表单侧不再有本机自定义模板这一层」；这个取舍由使用者决定（该诉求的使用密度本来就低）。

## 使用者可感知的变更

1. **输入框底部多一个入口**：「提示词库」。它与表单入口放在**同一个槽位条目**里 —— 槽位与注册
   数量都不变（各处的断言与 README 架构表因此只需改描述）。
2. **检索 → 预览 → 发送**：检索按**标题**匹配（上游 `/api/prompts/search`）；选中一条后再单独取
   全文（`/api/prompts/{id}`），所以列表页不会把一屏全文拖进来。留空查询则列出上游最新的一批
   （`/api/prompts?perPage=N`）—— **那条端点每条都带全文**（实测 `perPage=2` 约 27.9KB、`perPage=10`
   约 84.8KB），宿主取回后立即丢弃（`mapSearchResponse` 只留四个字段），因此那次响应本身并不小。这个
   落差来自上游端点的能力，不是选择。
3. **这条路径不经过构建器**：不做字段校验、不填进表单；发送的就是那段原文。界面上写明「未经本
   插件整理」，按钮文案是「发送原始提示词」—— 这是"不走规范检测"在界面上的表达。
4. **两个弹窗互斥**：打开检索会关掉表单，反之亦然；Esc 只关当前打开的那个。
5. 发送复用与表单成稿**同一条**链路（会话作用域的 `conversation.send`）。

## 为什么必须由宿主代发（本批的架构决定，有实测依据）

实测上游 `https://prompts.chat`：REST 端点公开可读、不需要 key，但**不返回 CORS 头**（预检
OPTIONS 返 204 却不回 `Access-Control-Allow-Origin` / `Allow-Methods`；`/api/mcp` 的 OPTIONS
直接 405）。浏览器半边因此无法直连。

改为：浏览器请求**同源**的两条路由（`/api/structured-prompt/library` 与
`/api/structured-prompt/library/item`），由 host 半边用 DSH 的
`ctx.connection.fetch.register({ path, methods, requestBody, fetch })` 注册（真实先例：
`packages/client/file-upload/src/index.ts` 的上传路由），host 侧用**全局 `fetch`** 去取上游。
三个后果值得记：

- host 产物**仍然零 import**（`fetch` / `Response` / `AbortSignal` 都是全局）—— 这条硬约束没有被
  新增的网络能力破坏。
- 上游地址成了**宿主侧配置**（`config.libraryBaseUrl`，缺省 `https://prompts.chat`）：要指向自托管
  实例只改配置。若当初把请求放在浏览器半边，这是做不到的 —— 客户端半边没有配置通道。
- 浏览器只与自己的宿主说话，不直接触第三方。

## 契约与不变量

- **黄金样本 25 条逐字未变**：检索结果与构建器完全隔离（`shared/library.ts` 不依赖任何
  `PromptForm` 类型，原文既不进表单也不经 `buildSystemPrompt`）。"不走规范检测"在代码结构上的
  落点就是这个。
- **`connection` 走 `ctx.get`，不写进 `inject`**（`inject` 仍只有 `['tools']`）：与 `delegate` 走
  `ctx.get('subagents')` 是同一条规则。没有 connection、或没有 `effect` 面（无法保证释放）时只跳过
  路由注册，工具照常可用。
- **安全边界三条**（都有断言）：① 基础地址只来自配置、**绝不接受请求参数**（否则这条路由就是任意
  URL 代理）；② 记录 id 先按 `isValidItemId` 校验再拼进上游路径（挡 `../`、`a/b`、`a?x=1`）；
  ③ 不向上游转发任何来自浏览器的请求头（只发 `accept`）。
- **失败归一**：上游超时 → 504、网络错 → 502、上游 404 → 404（"记录没了"，**只有取全文那条路**会这样
  判）、其余非 2xx → 502；都回可读说明而不是把异常抛给浏览器。检索那条路**不做** 404 特判 —— 那里的
  404 只说明上游没有这个端点（自托管版本或子路径配错），说成"没有这条提示词"会把人带偏。
- **响应形状稳定**：宿主映射一次 + 客户端再收敛一次（`mapSearchResponse` / `mapDetail`），界面因此
  与上游字段变化解耦。
- **断言**：工具套第 8 节（36 条）+ 渲染套第 8 节（20 条）。渲染套用 store 驱动状态（SSR 不能
  点击），网络层行为全部在工具套断言（`fetch` 可注入，不依赖真网络）。
- **"发送的就是检索到的原文"**：SSR 点不了按钮，但断言了**界面显示的原文与 `detail.content` 逐字
  一致**（发送用的正是同一个字段）。点击发送本身仍无断言 —— 这是 SSR 测试手段的边界，不是遗漏。

## 阻断：注册时序（本批最重要的一处）

第一轮审查抓到的阻断不在业务逻辑里，而在**装载时序**。`registerLibraryRoute` 原本在 `apply` 期用
`ctx.get('connection')` 读一次可选服务，读到 `undefined` 就跳过注册。问题在于"读不到"有两种含义 ——
"这个组装没有 web 载体"与"它还没就绪"—— 而后者在 DSH 里是常态：加载器的 entry 是**并行**创建的
（`vendor/loader/src/config/group.ts` 的 `Promise.allSettled`），各 entry 的 apply 先后没有保证，而
`connection` 要等 `credentials`，依赖链比本插件的 `tools` 长。

后果属于本仓库最怕的那一类：工具与表单全部正常、启动日志没有告警，只有两条路由不存在（浏览器
`fetch` 落到共享通道的 404，界面显示"宿主的响应不是 JSON"）。测试也抓不到 —— 假 ctx 的 `get` 同步
返回 connection，时序在测试里不可见。

修法：注册改走 `ctx.inject(['connection'], () => { ctx.effect(...) })` —— 服务就绪后才注册，失去时
随之释放。DSH 自己的 web 载体注册用的就是这个 API（`packages/client/modules` 里的
`ctx.inject(['webServer'], registerWebCarrier)`）。断言也改成"等就绪"而不是"读得到"：假 ctx 记录
`inject` 收到的依赖列表，并覆盖三条降级路径（没有 connection / 没有 inject 面 / 没有 effect 面 →
都不注册）。

**这条时序本身没有断言能覆盖**：假 ctx 只能证明"调用了 `inject`"，真正的验证要重启 DSH 看路由是否
注册（本批没做 —— 运行中的实例早于本批产物，且认证层先于路由匹配，探测不出结论）。

## 其余修复（第一轮 5 条需修）

| 问题 | 修法 |
| --- | --- |
| 「不向上游转发请求头」无从证明（`new Request` 会丢掉 `cookie` 这类 forbidden header，把 `request.headers` 原样转发的实现照样通过） | 测试改用**鸭子类型的假请求**（带真实 `Headers`），带上 cookie / authorization / origin / x-forwarded-for，断言上游只收到 `accept` |
| 「上游没有这条记录时给 404」名不副实：真实上游对未知 id 返回 **404**，会先命中"非 2xx"分支变成 502 | 上游 404 → 透传 404（"记录没了"）；上游 2xx 但缺正文 → 502（"上游给的东西不合预期"）。两条各自有断言 |
| 渲染假数据带 `description`，而上游检索端点不返回该字段 → 真实界面里列表只有标题与作者 | 假数据改成上游真实形状，并把"上游给了描述也渲染"单列为容错路径断言 |
| README 与归档说"列表很轻、不会把一屏全文拖进来"，对**空查询**不成立 | 文案据实改写（空查询走列表端点，每条带全文，宿主取回即丢） |
| 归档的断言计数失真（原写 25 / 12） | 改成实测值（工具套 29 条 / 渲染套 20 条） |

一并采纳的建议：上游请求改 `redirect: 'error'`（不跟随重定向 —— 否则 302 能把请求带去任意主机，
与"基础地址只来自配置"这条边界冲突）；配置的 `libraryBaseUrl` 改用 `new URL` 判（拒
`https://host@evil.example` 这类 origin 被改写的写法）；上游地址改**相对路径拼接**（自托管把实例挂在
子路径下时不再丢掉 `/sub`）；界面文案不再写死上游域名（`config.libraryBaseUrl` 可指向自托管实例）；
三个异步回调加请求序号，晚到的响应不再覆盖新状态（先点 A 再点 B 时详情与所选条目会错位）。

## 第二轮修复（5 条需修 + 采纳的 9 条建议）

| 问题 | 修法 |
| --- | --- |
| 上游 404 的文案被检索 handler 共用（检索端点 404 只可能是"上游没有这个端点"） | 404 特判**只留给 `handleLibraryItem`**；检索侧一律 502「上游返回 404」。两条路径各自有断言 |
| `ctx.effect` 挂在外层 ctx → "服务失去时释放"不成立 | 回调改用它的**参数作用域**（`ctx.inject(['connection'], (scoped) => scoped.effect(...))`），副作用因此挂在子 fiber 上、随服务释放；DSH 两处先例都是这个写法。**这是本轮唯一的实现级问题** |
| 第 8 节四条否定断言没沿用 `okHtml()`（渲染崩溃时假通过） | 第 8 节统一改用 `okHtml()` / `renderFailed()`；顺带给 `trigger()` 加同形的取用 |
| README 与归档的失败归一口径与实现不符 | 两处都改成"超时 504 / 网络错 502 / 上游 404 → 404（仅取全文）/ 其余非 2xx → 502" |
| 源码注释里还留着"列表很轻" | 改成"列表只带标题与作者；空查询走的那个端点带全文（约 85KB）" |

采纳的 9 条建议：`redirect: 'error'` 加断言；子路径保留（`https://host/sub`）加断言；
`https://host@evil.example` 的拒绝加断言；**配置拒绝带 query / fragment 的基础地址**（实测
`https://host/sub?x=1` 会拼成 `https://host/api/prompts?x=1`，`/sub` 静默消失）；非 JSON 响应与非 2xx
一样归一成 502 并加断言；浏览器取消分支（499）加断言；客户端与宿主的路由路径常量加**交叉断言**
（防止改一边忘另一边）；缺少 `ctx.inject` / `ctx.effect` 面时打日志而不是静默跳过；归档与 README 的
数字与口径按实测校正（行数、字节数、"容错路径"的表述）。

**未做**（记在这里而不是假装覆盖了）：客户端请求序号（挡住晚到的响应覆盖新状态）无断言 —— 三条
路径靠推演成立，SSR 里 `fetch` 不可达；`failure` 字段被列表与详情共用（同一时刻只有一处显示，影响
有限）；关闭弹窗不阻断在途响应写 store。

## 本批踩到的两处（值得记）

1. **单文件行数上限把三个文件逼着拆了**（上限 260，由 `tests/verify-install.mjs` 断言）：
   `host/library.ts` 279 → 247、`client/ui/LibraryModal.tsx` 277 → 223、`host/tool.ts` 265 → 259。
   拆法：上游请求与响应工具独立成 `host/library-upstream.ts`（90 行）；列表视图独立成
   `ui/LibraryList.tsx`（100 行）；`tool.ts` 里 `HostPluginContext` 的 JSDoc 压回两行。
2. **`Response.body` 只能读一次**：测试里断言与 detail 共用同一个 `Response` 时，第二次 `text()` 抛
   `TypeError: Body is unusable: Body has already been read` —— 整套以未捕获异常结束，**看不到任何
   FAIL 行**（只能靠读完整输出定位）。修法：先取文本，让断言与 detail 共用同一个字符串。

## 定点突变

| 突变 | 结果 |
| --- | --- |
| 去掉 `handleLibraryItem` 的 `isValidItemId` 校验 | 1 条红（非法 id 在边界被拒且不触碰上游） |
| 让上游请求带上 cookie 与 user-agent | 1 条红（不向上游转发浏览器请求头） |

三条各自只红对应断言 —— 本批的三条安全/隐私边界都能被单独证伪。

## 评估后决定不做

- **浏览器直连**（即使将来上游加了 CORS 头）：那会把"上游地址"变成客户端的事，而客户端半边没有
  配置通道，自托管将无法配置。
- **把检索结果填进表单**（"用这段提示词预填 17 个字段"）：那要求把成品文本结构化回字段，属于
  猜测；用户明确要求检索结果不走规范。
- **工具侧检索**（让模型自己搜提示词库）：本批只做人的入口；工具侧要新增一个触网工具，收益与成本
  都还没有数据。
- **结果缓存**：上游响应本身是 `no-store` 语义（Vercel 侧 `Cache-Control: public, max-age=0,
  must-revalidate`），插件再缓存只会引入失效问题。
