# v0.3.1 —— 重启前的 404 引出的三处修补（2026-10）

## 起点：一次真实的失败

v0.3.0 合并后，使用者在界面上搜「SQL 优化」，得到「宿主的响应不是 JSON（HTTP 404）」。

诊断（客观证据，不是猜）：监听 19387 的 DSH 进程启动于 **14:44:01**，而 v0.3.0 的产物写入于 **15:33:52**
—— 宿主跑的是 49 分钟前的代码。客户端 bundle 会在页面刷新时从 `lib/client.js` 重新取，而 **host 侧的
路由注册只在启动时发生一次**，于是出现"界面是新的、宿主是旧的"：检索请求落到共享通道的兜底 404。

**重启 DSH 即解决**，这不是代码缺陷。但这次失败暴露了三处该修的地方。

## 一处真缺陷：客户端拿错了映射函数（本批最重要）

在给响应加"数据来源"字段时发现：客户端的 `searchLibrary` 用 `mapSearchResponse` 去解析**宿主已映射**的
响应 `{ items, total }`，而那个函数读的是**上游**形状 `{ prompts: [...] }` —— `prompts` 永远不存在，于是
**每次检索都被缩成空列表**。宿主与界面各自都对，错在中间这一层拿错了函数。

严重性：这条路径在成功时**完全不可用**（列表永远为空）。它此前没被发现，是因为测试分工恰好绕开了它：
渲染套驱动 store（不经过 client 的映射），工具套当时只覆盖 host 侧与失败分支。**两轮独立审查也都没抓到** ——
它们查的是路由契约、断言强度与归档口径。

修法与守护：客户端改为逐条过 `mapItem`（单条容错映射，形状由宿主保证），并补上"客户端成功路径"的断言
（`items` / `total` / `source` 三项都不丢）—— 这条断言现在能单独证伪那个错误。

## 使用者可感知的变更

1. **报错变成可执行的**：宿主没有这条路由时（典型原因就是 host 侧改动没重启），界面直接说
   「宿主没有这条检索路由：host 侧的改动要重启 DSH 才生效」，而不是「宿主的响应不是 JSON（HTTP 404）」。
2. **来源标注**：界面底部显示数据来源 —— 默认 `prompts.chat`，自托管时是你的实例域名。来源名由宿主在
   响应里带回（`source` 字段），所以它跟着配置走，客户端不写死。
3. **README 增加「来源与致谢」节**：写清两件事 —— 本插件只调用上游的公开只读接口、不打包其代码与数据；
   以及上游的**双许可**（源码与站点自产内容 MIT；**提示词内容与数据 CC0 1.0**，依据其 `LICENSE` 文件），
   并点名致谢其作者与社区贡献者。

## 契约与不变量

- 黄金样本 25 条逐字未变（本批不碰构建器）。
- `source` 走**数据流**而不是配置下发：上游响应本身没有这个字段，宿主在返回前注入
  `new URL(base).host`。这样"来源标注跟着配置走"不需要客户端读配置 —— 客户端半边本来就没有配置通道。
- 新增断言：客户端成功路径（覆盖上面那个真缺陷）、宿主注入来源名、来源名随配置变化、界面来源标注随响应
  变化、404 的可执行提示。
- 断言计数（实测）：工具套第 8 节 43 条、渲染套第 8 节 22 条。
- **跨半边的那一步也有守护了**：审查指出"响应 → store 的 `source`"此前没有断言（把组件里那行写入删掉，
  两套测试全绿）。因此把收敛（`toSearchResult`）与 patch（`searchPatch`）都抽成纯函数并各加断言；形状
  漂移（宿主回了 `{ prompts: [...] }` 这类错配形状）现在给出说明，而不是静默当成"没有命中"。

## 采纳（第三轮 9 条建议）

| 建议 | 处理 |
| --- | --- |
| 「响应 → store 的 `source`」没有守护 | 抽出 `toSearchResult` 与 `searchPatch` 两个纯函数并各加断言；突变验证：抽掉 `source` 写入 → 恰 1 条红 |
| 收敛层对形状漂移静默（给空列表 + `ok: true`） | 缺 `items` 时给出可读说明（与 404 那条对称），不再落到"没有命中任何提示词"；突变验证：去掉该分支 → 恰 1 条红 |
| `total` 兜底两处不一致（宿主 `0` / 客户端 `items.length`） | 客户端统一成 `0`（"未知"），与宿主一致 |
| 仓库根没有 LICENSE 文件（README 与 package.json 都声明 MIT） | 补标准 MIT 全文 |
| 来源名只用 `host`，自托管挂子路径时同域两个实例分不开 | 改成 `host + pathname`（`https://host/sub` → `host/sub`），断言同步 |
| 失败分支不重置 `source`（失败态仍显示上次成功的来源） | 失败时一并清空 |
| 归档审查记录仍是"进行中" | 本表 |
| 遗留两条：`lib/*.js` 换行；`test-render.mjs` 里 1 处缺渲染成功前提的否定断言 | 录入「待决策」，非本批引入 |
| 真实界面验证需重启 DSH（19387 的进程仍是 14:44:01 启动） | 已知前提，见本文件开头 |

## 评估后决定不做

- **把来源名做成可配置的界面文案**：现在的做法（宿主回填 host）已经覆盖自托管，再为改一个词开一条
  "客户端读配置"的通道不值。
- **在界面上放许可全文**：README 里写清关系与链接即可；界面空间有限，标注来源名足够。

## 待决策

- v0.2.4 / v0.3.0 遗留的两条（`lib/*.js` 换行、既有"不该出现"断言缺渲染成功前提）仍未处理。
- **测试分工的盲区**：这次是"渲染套驱动 store + 工具套只测 host 侧"造成的缝。将来再加跨半边的数据流，
  应当**默认补一条"客户端解析宿主响应"的断言**，而不是依赖某一侧的覆盖。
