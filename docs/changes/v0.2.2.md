# v0.2.2 —— 模板库外置与「模板 / delegate」的说明修正（2026-10）

本文件归档自 v0.2.1 起的改动：改了什么、为什么这么改、哪些选择是权衡后定下的。这一批的起点
是一次上下文消耗诊断（见下节），结论是**插件不是当时的成本源**，于是改动集中在「让插件更容易
被用对」而不是「省插件自己的字」。

分支：`feat/template-library`。

## 起点：一次上下文诊断

在 `session-e7ccd8f8`（200 步）上统计真实用量：首步基线 22,137 tokens，末步 465,098；增长里
`read` 工具结果占 59.2%、`edit` 15.8%、`grep` 8.8%、`pwsh` 8.3%、`subagent_fork` 5.0%；41 条
超过 8k 字符的工具结果占了工具结果字符总量的 51.6%。

同一份扫描给出插件自己的用量：29 个会话里 `build_structured_prompt` 只被调用 10 次，表单成稿
投递 0 条。**所以这一批没有去优化插件产出的字数**（那是拿提示词质量换一个不是瓶颈的数字），
而是修了两个「用不对就白花」的地方：

1. `template` 只有一个 id 枚举，没有任何场景说明 —— 模型无从判断该选哪套，于是干脆自己填所有
   字段，模板库等于白放。
2. `delegate` 只写了「keeps long prompts cheap」，没写什么时候该用、什么时候不该用。

## 使用者可感知的变更

1. **模板库 4 套 → 8 套**。保留 4 套领域样例（告警研判（原始示例）、代码审查、数据提取、报告
   撰写），新增 4 套**形态型**：`explore`（探索调研）、`implement`（实现改动）、`debug`（故障
   定位）、`handoff`（交接归档）。形态型模板把「先读后结论」「最小改动 + 真实验证」「证据优先」
   「区分已完成与未开始」这类约束与任务形态绑定，模型只需给 `role`/`goal` 与少量覆盖。
2. **`template` 的说明带出每套的一句话场景**（`whenToUse`），模型据此挑选。
3. **`delegate` 的说明重写**：明确它是**可选**路径，说明什么时候值得用（本会话历史已长、或任务
   需要大范围探索），并点出**首轮的风险** —— 子代理独立运行、看不到本会话，任务尚未澄清时委托
   等于把手头信息最少的那一版交出去。
4. **未委托分支的返回多了一句成本陈述**：说明这段文本会留在上下文并在之后每一步重放，带
   `delegate` 的调用可以让下一份不进来。它是陈述事实（模型自己决定），不是把它推成默认路径。
5. **模板数据外置到 `src/shared/templates.json`**。以前模板硬编码在 `templates.ts` 里，改一套
   模板要动代码；现在 JSON 是单一真源，表单下拉、工具的 `template` 枚举、黄金样本都从它取值。

## 为什么 JSON 走「直接 import」而不是「构建期生成」

实测（本机 tsdown，探针见下）：`import data from './x.json'` 会被**内联**成字面量 —— host ESM
与 client CJS 两个产物里都只留 `//#region src/shared/templates.json` 加数据，静态 `import`、
动态 `import(`、`require(` 全部为 false。于是 host 半边「零 import」的硬约束不受影响。

对比另一条路（构建期把 JSON 生成成 `.ts` 并入库）：那样要多出「生成脚本 + 生成物入库 + 防漂移
断言」三个部件，而"改了 JSON 忘了重新生成"正是这个仓库反复踩的那类缺陷。直接 import 只有一个
数据文件 + 一行导入 + tsconfig 一个开关（`resolveJsonModule`）。

JSON 是**文件边界**，所以 `templates.ts` 里对字段形状校验一次：复用导入校验那份 `FIELD_SHAPES`
与 `matchesShape`（`forms.ts` 导出），字段名写错、类型不符、越界枚举都会在构建/启动期报错，而不是
把坏值塞进表单。

## 契约与不变量

- **黄金样本 20 → 24 条**：新增的 4 条锁住新模板的产物。原有 20 条**逐字未变**（JSON 里的 4 套
  领域模板是从原代码逐字搬运的）。
- **工具 schema 变大是刻意的**：8 套 × 一句场景 ≈ 130 字，而 schema **常驻**上下文（那条 200 步
  会话的首步基线里就有它）。这就是模板不能无限加的原因，也是模板数量、`whenToUse` 长度都被断言
  盯住的原因（`whenToUse ≤ 40 字`）。
- **移除 `ALERT_TRIAGE_FIELDS` 导出**：模板库改由 JSON 驱动后，测试改用 `TEMPLATES[0].build()`。
- **新增断言**（并入既有「文档契约」套，不新增第九套）：模板 JSON 的版本号、每套模板的必填字段、
  id 唯一且为 kebab-case、字段名与取值符合表单形状、每套都填了 `role`/`goal`、`whenToUse` 长度、
  每套都能构建出以 `# 身份` 开头的提示词；工具侧断言 `template` 描述里带出每套场景；README 的
  文件清单断言扩展到 `.json`，收集范围也扩到仓库根（否则 `package.json` 会被误判为不存在）。

## 待决策（刻意没做）

- **表单侧的「直投子代理」出口**：现在工具（模型）有 `delegate`，而表单（人）只有「复制 / 发送」，
  人构建的长提示词只能走最贵的那条路。技术上客户端已有 `ConversationAttachmentFace.sendSession`
  与 `fileUpload` 可用（把成稿变成附件、主上下文只留短指令），但这要新增服务依赖，破坏现在
  「`inject` 只有 `slots`」的契约与它的断言 —— 属于插件定位的变化，留给你定。
- **工具结果裁剪与历史摘要**：那是 DSH `compaction` / `tool-result-pruner` 的职责（你的 desktop
  合成树里这三个条目是 `disabled: true`），插件既无职责也无接口。
