# v0.2.4 —— 让模板的场景在表单里可见（2026-10）

本文件归档这一批改动：它把每套模板的一句话场景（`whenToUse`）从"只在模型工具 schema 里"带到
**表单界面**上，并对冲 v0.2.3 放宽 `role`/`goal` 之后留下的语义风险（只选模板、不复述具体任务，
产物随之变泛）。

分支：`feat/template-hint-in-form`（当前改动在工作区，提交时先建分支）。

## 起点：v0.2.3 留下的两个指标

v0.2.3 放宽参数边界时留下两个待复测指标：`template` 使用率（改前 3/10）与"只选模板但没复述具体
目标"的比例。第二个是那次放宽引入的语义风险，而 host 侧只能靠 `goal` 的描述**引导**，不能保证。

本批把这条引导搬到**人**看得见的地方：人不读工具 schema，只读表单。

## 使用者可感知的变更

1. **模板下拉的选项带出场景**：`label · whenToUse`（例如「代码审查 · 审查一处改动，找缺陷并排序」）。
   下拉加了宽度约束（`maxWidth: 260`）——**选项文本本身**变长，不加约束时最长的选项会把底部那
   一行的导入/导出/清空挤下去。
2. **套用模板后表单顶部出现场景条**（`data-applied-template`）：写明该模板的 label 与场景，并提醒
   「模板里的目标是形态化的，请把本次的具体任务写进「目标」」。这条提示只进界面、不进提示词 ——
   它要提醒的正是"别只选模板"。
3. **场景条是界面陈述，不是产物的一部分**：成稿只由表单字段决定。手改字段、关闭重开、切换会话
   都不会清掉它；只有「清空」与「导入」会清；记的 id 解析不到（例如来自已删除的模板）时整条不渲染。

## 契约与不变量

- **黄金样本 25 条逐字未变**：本批只动界面，产物零漂移 —— 这是"场景条不参与构建"的第一层证据
  （第二层是渲染套里那条逐字比对，见下）。
- **`appliedTemplate` 进 store，而不是组件本地状态**：离线渲染测试只能驱动 store，组件本地状态在
  SSR 下不可观测（等于没有守护）。这条取舍写在这里，免得下次又用本地状态接界面反馈。
- **id → 模板的解析收敛到 `findTemplate`**（新增于 `src/shared/templates.ts`）：host 的构建、
  表单下拉的选择回调、容器对 `appliedTemplate` 的解析都走它。将来再加一层模板来源（例如本机
  自定义模板）只需要改这一处 —— 这就是 C 项的接缝。
- **解析在容器（`Panel`），`Modal` 只渲染**：`Modal` 的 props 是 `applied: PromptTemplate | undefined`，
  不是可选属性（`exactOptionalPropertyTypes` 下显式传 `undefined` 需要联合类型，见「修复过程」）。
- **场景条用 `role="note"`** 而不是 `status`：它是持久的状态陈述，不需要播报；底部栏的 notice
  已经占了 live region，同页两个只会变噪音。
- **断言 13 条**（并入「渲染结构」套，不新增第九套）：下拉所在面板可渲染、下拉 8 套场景齐全、
  下拉有宽度约束、场景条渲染 / label 与场景配对 / 措辞提示 / 只渲染一条、关闭重开不清标记、
  手改字段不清标记、未套用不渲染、解析不到不渲染、清空清标记、**标记不参与产物**、补回字段值后
  预览区重现正文。其中「关闭重开」「手改字段」两条是第二轮审查提的：README 声称的边界必须有
  断言守护，否则只有文档、没有守护。
- **"不该出现"的断言必须同时确认渲染成功**：`render()` 把抛错收成空 HTML，于是
  `!html.includes(...)` 会在渲染崩溃时**假通过**。本批踩到过（见「修复过程」）；7b 节现在统一
  用一个取用函数 `okHtml()`：**该出现**的断言拿它取 HTML（失败时 detail 里带渲染错误，不必靠猜），
  **不该出现**的断言用它先确认渲染成功（崩溃时返回带标记的文本，断言必红）。

## 修复过程（含两处由修复引入的回归）

按第一轮意见修完后，**修复本身引入了两处回归**，都被既有防线抓住：

1. `Panel` 把模板传给 `Modal` 时键名没跟着改（`Modal` 的 prop 已从 `appliedTemplate` 改名
   `applied`）→ `applied` 恒为 `undefined` → 场景条彻底不渲染。**类型检查套先红**（TS2322：该属性
   不存在），渲染断言跟着红一片。
2. 改成 `applied?: PromptTemplate` 后，`exactOptionalPropertyTypes` 拒绝显式传 `undefined` →
   类型检查红（TS2375）。改成 `applied: PromptTemplate | undefined`，这才是实际契约（父组件总是传，
   值可能为 `undefined`）。

顺带发现并修掉一处**测试自身的弱点**：`未套用模板时不渲染场景条` 这类"不该出现"的断言用的是
`!panel().html.includes(...)`，而 `render()` 把渲染抛错收成空 HTML —— 上面第 1 处的崩溃期间，这几条
断言**全部假通过**（整套 37 条红里它们显示 OK）。7b 节现在统一用取用函数 `okHtml()`：两类断言都先
经过"渲染是否成功"这一关。

本仓库记过同类事故的先例 —— README「改动流程」第 4 条写明"本仓库真实发生过「修复本身引入回归」
（v0.2.1 的 `{form:{...}}` 从硬失败变静默清空）"。本批这次是同一性质的新事例，两条都被**既有**验证套
抓住，说明防线有效；也再次说明"修完即完"是错的 —— 所以按流程对受影响的文件做了第二轮审查。

## 评估后决定不做

- **把 `<option title>` 当场景的展示路径**：浏览器不据此渲染 option 提示。保留它只作辅助技术的
  兜底，场景的展示靠选项文本本身（注释已写明这一点）。
- **场景条随字段改动消失**：它陈述的是"这份表单从哪套模板起步"，用户手改字段并不改变这个事实；
  只有换模板、导入、清空会改变它。
- **为同页两个 live region 引入额外机制**：把场景条改成 `role="note"` 即可。

## 待决策（本批未做）

- **`lib/*.js` 的换行**：`.gitattributes` 只钉了 `tests/golden/*.txt`，产物入库后他人 checkout 得到
  CRLF、与本地构建产物不同字节（`git status` 的 `LF will be replaced by CRLF` 警告）。非本批引入，
  但本批把产物列为审查对象时又碰到它；改它会影响全仓规范化，单独一批处理。**叠加效应值得记**：
  本批的 `lib/client.js` diff 有 296/256 行，主因不是内容漂移，而是 tsdown 的 region 排序变化 ——
  `//#region src/shared/templates.json`（含新增的 `findTemplate`）从文件尾部搬到了中段。产物比对
  成本就是这样被抬高的，下一批一并处理换行时顺带看它。
- **既有 12 条"不该出现"型断言仍未加渲染成功前提**（第二轮 S2）：它们可在渲染崩溃时假通过
  （`tests/test-render.mjs` 第 1–6 节的那些 `!html.includes(...)`）。非本批引入；本批只把 7b 节的
  四条按新写法处理，统一补前提取用函数会碰十几条既有断言，单独一批做。
- **C 项（本机自定义模板长期化）**：方案已出（插件内新开一个 Cordis 服务 + localStorage 单键 +
  `inject` 的 `hooks` 隔间给组件），本批只留下两处接缝：解析函数唯一（`findTemplate`）、解析在容器。
  另注意 `Modal.tsx` 已 250/260 行 —— C 项的界面改动**必须先抽文件**（例如先把场景条抽成
  `AppliedTemplateNote.tsx`），别等越限才动。
