# v0.3.1

从上一个 tag（`v0.2.3`）到现在，这个插件从"一个结构化提示词构建器"长成了**两个可独立装载的组件**。
以下是使用者能感知的变化。

## 新增

### 提示词库检索（请求由宿主代发）

输入框工具栏的「提示词库」按钮：检索 [prompts.chat](https://prompts.chat) 上的公开提示词，列表 → 原文预览
→ **直接发送进会话**（或复制）。

- 检索结果**不进构建器**：那是别人写好的成品文本，因此不做字段校验、不填表单。检索与构建各走各的路径。
- 请求由**宿主**代发：上游不返回 CORS 头，浏览器直连会被拒。副作用是好的 —— 上游地址成了宿主侧配置
  （`config.libraryBaseUrl`，缺省 `https://prompts.chat`），换自托管实例只改配置、插件代码不动。
- 界面上标注数据来源（跟着配置走），并致谢上游：它是**双许可**项目 —— 源码与站点自产内容 MIT，
  **提示词内容与数据 CC0 1.0**。本插件只调用其公开只读接口，不打包、不分发它的代码或数据。

### 表单的模板场景

八套模板（4 套任务形态 + 4 套领域样例）在下拉里各带一句场景说明；套用后表单顶部出现一条场景条，提醒把
本次的具体任务写进「目标」—— 模板带的是形态化目标，不复述具体任务时产物会变泛。场景条是**界面陈述**，
不参与提示词构建（改它不会改产物一个字节）。

### 两个可独立装载的组件

`cordis.patch.yml` 现在是两条装载行，各自带 `config`、可单独 `disabled`：

| 装载行 | 提供 | 配置 |
| --- | --- | --- |
| `dsh-plugin-structured-prompt` | 结构化提示词（表单 + 模型可调用的工具） | `provider` |
| `dsh-plugin-structured-prompt/library` | 提示词库检索 | `libraryBaseUrl` |

配置各归其位：`provider` 归结构化、`libraryBaseUrl` 归提示词库。**第一条必须保留精确包名**（不能改写成
包子路径）：DSH 的 client 半边只认精确包名的装载行。

## 修复

- **提示词库检索曾返回空列表**：客户端拿"上游形状"的映射器去解析宿主**已映射**的响应，成功路径实际
  不可用（宿主与界面各自都对，错在中间那一层）。已修，并补了能单独证伪它的断言。
- **注入样式曾打坏结构化弹窗**：样式表里的选择器被写成逗号分隔的独立列表，裸属性选择器于是无条件命中
  弹窗根元素 —— 弹窗塌成 10px 高、整棵子树半透明（真实浏览器实测）。改用**共享属性**后，不再依赖
  "每加一个组件都要把样式改一遍"。
- **两个入口曾一起消失**：两条装载行都写成包子路径时，DSH 的 client 模块系统不会把它们当作 client row，
  client bundle 完全不加载。已改回"恰有一条精确包名"，并加了断言守住这条约束。
- 宿主没有那条检索路由时（典型原因是 host 侧改动没重启 DSH），界面现在直接说明该做什么，而不是显示
  一句"宿主的响应不是 JSON（HTTP 404）"。

## 升级

```powershell
dsh plugin --profile desktop add github:YuChenLiao/dsh-plugin-structured-prompt
```

装完**重启 DSH**（host 侧的工具注册与路由注册都发生在启动时；客户端 bundle 会随页面刷新更新，这也是
"界面是新的、宿主是旧的"会发生的原因）。

## 已知边界

- host 产物是**零运行时 import** 的打包结果，因此插件自身不需要 `npm install`，也没有 devDependency。
- 提示词库弹窗与结构化表单弹窗现在**可以同时打开**（拆分前它们共用一条注册、互斥）。
- 上游是第三方服务；指向自托管实例只需改提示词库那条装载行的 `config.libraryBaseUrl`。
- 模板库数据在 `src/components/structured/shared/templates.json`（表单下拉、工具枚举、黄金样本同源）。
